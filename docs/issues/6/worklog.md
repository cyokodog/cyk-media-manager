# Issue #6 作業ログ

https://github.com/cyokodog/cyk-media-manager/issues/6

## 2026-09-06 フッターのリネーム設定UIとプレビュー・衝突検査を伴うリネーム処理

これで #1 の一連（#2〜#7）が揃い、リネームが実際に動くようになった。

### サーバー: plan / apply に分割した

元の `/api/rename` は計画を立てずに実行するため、プレビューが作れなかった。

- `POST /api/rename/plan` — 計画のみ返す。ファイルシステムは変更しない
- `POST /api/rename` — **同じ計画をサーバー側で再計算**して実行する

**クライアントから `to` の名前は受け取らない。** ブラウザ側で計算した名前を
サーバーが信用すると、プレビューと実行が食い違いうるため。

### 衝突判定は小文字化して比較する

macOS の APFS は既定でケース非依存で、`A.PNG` と `a.png` は同じファイルを
指すが、文字列比較では別物になる。拡張子は小文字化される仕様なので、
`IMG_0002.PNG` → `花_ひまわり_0020.png` と既存の `花_ひまわり_0020.PNG` が
衝突するケースが**実際に起こりうる**（このマシンで `existsSync` の挙動を
確認済み）。`toLowerCase()` して比較している。

判定は2種類:

- `exists` — 対象外のファイルが既にその名前を使っている
- `duplicate` — 計画内で同じ名前が複数回現れる

この計画でリネームされて「いなくなる」名前は衝突扱いにしない。

### ロールバック

`from` → `.__tmp__` → `to` の2段階。第1段階で直接 `to` へ動かすと、計画内で
名前が入れ替わる場合に上書きが起きる。

失敗時は完了済みを戻してから退避中のものを戻す。`applyRenamePlan` は
`fsImpl` を差し替えられるようにしてあり、**`renameSync` に失敗を注入する
テストで両方の段階を検証した**。ロールバック経路はテストが無いと壊れていても
気づけないため。

`server.js` は `require.main === module` で `listen` を囲み、テストから
require してもサーバーが起動しないようにした。

### 入力値のガード

`clampInt` で桁数 1〜10、ステップは 1 以上に丸める。ステップ 0 は全件が
同じ名前になり必ず自己衝突する。クライアント側にも同じ関数を置いて、
プレビューと実行の計算を一致させている。

### 決めたこと

- **モーダル内に開始番号の入力を置いた。** デザイン（`RenameModal.dc.html`）に
  あり、衝突をその場で直せる。フッター側の値とも双方向に連動する
- **衝突が1件でもあれば実行ボタンを無効化。** スキップや上書きの選択肢は
  出さない（#1 の決定どおり）
- リネーム後は `/api/images` を読み直し、`targetOrder` を**新しい名前**で
  組み直す。古い名前を保持しようとしない
- #3 で `disabled` にしていたフッターの入力を有効化した

### 検証

`npm test` で53テスト（既存33 + 新規20）すべて通過。

**ユニットテスト11件**（`e2e/rename-unit.spec.js`）— 計画の組み立て、拡張子の
小文字化、衝突検出（対象外・ケース違い・計画内重複）、開始番号での回避、
`clampInt` の丸め、名前が入れ替わる計画、そして**失敗注入による
ロールバック2ケース**。

**UIテスト9件**（`e2e/rename-ui.spec.js`）— 確定ボタンの有効・無効、出力例の
表示、連番の連動、プレビューの一覧、衝突の判別と実行不可、モーダルでの
開始番号変更による回避、実行と対象外ファイルの不変、実行後の並び順保持。

**リネームは破壊的なので、UIテストは `os.tmpdir()` に使い捨てディレクトリを
作って実行している。** `e2e/fixtures` には触らない（テスト後も無傷であることを
確認済み）。

スクリーンショットでプレビューと衝突警告を目視確認した。

### ハマった点

プレビューはサーバー往復があるため、`click('#previewBtn')` の直後に
モーダルの中身を読むと空になる。`toBeVisible()` や `toHaveCount()` で
待つ必要がある。リネーム後も `/api/images` の読み直しがあるので同様。

最初これでテストが失敗し、アプリ側の不具合かと切り分けたが、
デバッグしたところ3行とも正しく描画されていた（テスト側の問題だった）。

### 検証していない点

- **実ブラウザでの手動操作**。ヘッドレス Chromium のみ
- 大量ファイル（数百件）でのプレビュー表示とリネーム
- リネーム中に外部からファイルが変更された場合の競合。実行直前に
  存在確認はしているが、その後の変更は検知できない
